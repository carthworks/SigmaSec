Shared infrastructure

Nearly every workflow below passes through the same five pieces before it touches business logic. They're documented once here instead of repeated in every card.

ComponentWhereRole
DB sessiondatabase.py → get_dbFastAPI dependency yielding one SessionLocal() per request, closed in a finally. Pool size 10, overflow 20.
JWT issuanceauth/jwt.py → create_access_token / verify_tokenHS256, 8h expiry, secret from JWT_SECRET.
Current userauth/dependencies.py → get_current_userDecodes the bearer token, loads the User row, 401s on invalid/inactive.
Tenant scopingauth/dependencies.py → get_user_org_idReads org_id only from the JWT-derived user — never from the request body or query params. This single function is the multi-tenant isolation anchor for almost every query in the app.
Role gateauth/dependencies.py → require_role(*roles)Dependency factory; 403s if current_user.role isn't in the allowed set.
App wiringmain.pyMounts every router, CORS, rate limiter, and a startup hook that alters the findings table and runs Alembic migrations.
Security note main.py and routers/scans.py both expose GET /test-export-debug and GET /restart-backend with no auth dependency at all — the latter calls os._exit(0), so any unauthenticated caller can kill the backend process.
01

Auth & onboarding

A brand-new tenant starts here: signup creates both the Org and its first admin User in one transaction.

Sign up

POST /auth/signup public
routers/auth.py → signup

Validated by schemas/auth.py:UserSignup — email format, password ≥ 8 chars, org name ≥ 2 chars.

db.query(User).filter(email==…)

Uniqueness check before anything is created.

models/org.py → Org(…)

Slug generated + collision loop, then db.add(org); db.flush() to get org.id without committing yet.

pwd_context.hash(password)

bcrypt, 12 rounds.

models/user.py → User(role=admin, is_verified=False)

db.add(user); db.commit(); db.refresh(user) — org and admin land in the same transaction.

The tenant-creation entry point: one call produces a new Org and its first (admin-role) user. No auth required, since there's nothing to authenticate against yet.

Log in

POST /auth/token public · OAuth2 password grant
routers/auth.py → login → db.query(User).filter(email==form_data.username) → pwd_context.verify(password, hashed) → check is_active → jwt.py:create_access_token({sub, org_id, role, email}) → TokenResponse (8h)

org_id and role are embedded directly in the JWT payload, so every later request can resolve tenant and permissions without an extra DB lookup.

Get current profile

GET /auth/me auth required
routers/auth.py → get_me → Depends(get_current_user) → returns the loaded User row
02

Users & orgs

Everyday tenant administration — creating teammates and, separately, platform-level org management.

Create a user

POST /users admin only org-scoped
routers/users.py → create_user

Gated by require_role("admin") + get_user_org_id — org_id comes from the caller's JWT, never the request body.

schemas/user.py → UserCreate

Password strength validator: ≥ 12 chars, upper/lower/digit/special, blocklisted common passwords, ≤ 72 bytes (bcrypt's limit).

db.query(User).filter(email==…)

Email uniqueness check.

pwd_context.hash(password) → models/user.py:User(org_id=org_id, …)
database.py:get_db → db.add(user); db.commit(); db.refresh(user)

This is the canonical shape every write endpoint in this app follows: router function → role gate → schema validation → uniqueness check → ORM object → get_db session → add/commit.

List users

GET /users admin · analyst
routers/users.py → list_users → require_role("admin","analyst") → db.query(User).filter(org_id==org_id).all()

The org_id filter is explicit in the code with a comment flagging it as critical — this is the query that must never leak another tenant's users.

Create / list orgs

POST · GET /orgs admin only
routers/orgs.py → create_org / list_orgs → require_role("admin") → Org(…) → db.add/commit | db.query(Org).all()

Platform-level operation, not tenant-level — list_orgs intentionally has no org_id filter, since it exists for cross-tenant onboarding, not day-to-day use.

04

Scans pipeline

The core of the platform. A single POST /scans kicks off a chain of Celery tasks that fan out across four scanner adapters, reconcile results, enrich them with threat intel and AI, then quietly notify Slack — all off the original request thread.

Create scan

POST /scans admin · analyst rate-limited
routers/scans.py → create_scan

10 scans/hour/IP via the limits library.

validate_target()

Blocks RFC1918 / loopback / localhost targets — the SSRF guard for the whole scan pipeline. The scanner adapters themselves don't re-check this.

scan_types ⊆ {vuln, sca, secret, opengroup}

Auto-creates an Asset if asset_id wasn't given, deduped by org_id+target.

models/scan.py → Scan(status="queued") → db.add/commit/refresh

Followed by write_scan_audit_log() → an AuditLog row.

tasks/scan_tasks.py → run_scan_task.delay(…)

Queued onto the Celery/Redis broker; scan.celery_task_id is saved back before the response returns.

Async execution — scanner fan-out

celery worker parallel
tasks/scan_tasks.py → run_scan_task

Scan.status = "running", then one Celery subtask signature is built per requested scan type.

run_nuclei_scan_subtask / run_trivy_scan_subtask / run_gitleaks_scan_subtask / run_opengroup_scan_subtask

Each calls its adapter's safe_run() — NucleiAdapter, TrivyAdapter, GitleaksAdapter, OpenGroupAdapter — via the shared adapters/runner.py:run_logged_command.

Redis hash scan:{scan_id}

Tracks status, progress_pct, current_step, counts — polled live by the SSE progress endpoint below.

check_scan_timeout_task.apply_async(countdown=1800)

A 30-minute watchdog that fails the scan if it's still running.

celery.chord(group(header_tasks))(scan_completed_callback.s(…))

Fan-out / fan-in: all four subtasks run in parallel; the callback fires only once every one of them has finished.

Completion & reconciliation

scan_completed_callback
flatten all subtask results → save_findings(db, all_findings)

Fingerprint-based upsert: an existing Finding with a matching fingerprint is updated in place, otherwise a new row is inserted. This is the single place all four adapters' output converges.

_apply_trivy_fp_heuristic() / _apply_gitleaks_fp_heuristic()

Heuristic false-positive tagging layered on top of the raw adapter output.

reconciliation pass

OpenGroup (SAST) findings from a prior scan that are no longer reported this time get auto-marked FindingStatus.fixed.

redis.delete("executive:{org_id}") → enrich_findings_task.delay(scan_id)

Invalidates the cached executive summary, then hands off to the enrichment chain. Scan.status = "complete".

Enrichment chain — intel → AI → Slack

enrich_findings_task → ai_enrichment_task → post_slack_summary external I/O
intel/nvd.py:NVDClient.get_cve_metrics() → intel/kev.py:KEVClient.is_cve_kev() → intel/epss.py:EPSSClient.get_epss_scores()

CVSS score/vector, CISA KEV listing, and EPSS exploit-probability — all Redis-cached, batched where possible.

ai/reachability.py:determine_cve_reachability()

For Trivy findings: clones the asset's repo, AST-walks it for import/call-site evidence, then asks the LLM to classify reachable / unreachable / uncertain. OpenGroup findings get a simpler direct file-existence check, no LLM call.

priority_score = epss × cvss × kev_multiplier × asset_weight × reachability_multiplier

Then RANK() OVER (PARTITION BY scan_id) in SQL computes priority_rank.

ai_enrichment_task.delay(scan_id)

Trivy/OpenGroup findings processed in batches of 5 via a ThreadPoolExecutor → ai/prompt_builder.py:enrich_finding() → ai/claude_client.py:AIClient (Ollama by default, or Anthropic if AI_PROVIDER=anthropic). Every call writes an AICall row for cost tracking.

generate_exec_summary_if_needed() → Scan.exec_summary

A 3–5 sentence CISO-facing paragraph, cached on the Scan row.

post_slack_summary.delay(scan_id) → SlackConfig lookup → utils/encryption.py:decrypt_value(webhook_url) → slack_sdk.WebhookClient.send()

Skipped entirely if the org's Slack config is "critical only" and nothing critical/KEV-listed was found.

Design note Intel → AI → exec-summary → Slack is a linear chain of .delay() calls nested inside each task's success path — not an orchestrated Celery chain/chord. A silent crash partway through leaves every later stage permanently un-triggered, with no retry.

05

Findings

Triage, remediation, and ticketing built on top of whatever save_findings() persisted.

List / filter findings

GET /findings
routers/findings.py → list_findings → org-scoped query: scan_id, asset_id, severity, status, exploit_validated, fp_candidate, free-text q (ILIKE) → schemas/finding.py:FindingOut (model_validator flattens ~30 ORM fields)

Tag filtering happens in Python after the query returns, not in SQL — a deliberate "database-agnostic" tradeoff called out in the code, since JSONB array containment isn't portable.

Get / update / tag a finding

GET · PATCH /findings/{id} · POST/DELETE …/tags
get_finding → org-ownership 403 check update_finding → mutate status / fp_candidate / jira_issue_key / pr_url → db.commit add_finding_tag / remove_finding_tag → mutate the JSONB tags array

AI-assisted finding review

POST …/regenerate-ai · GET …/ai-enrichment admin only AI call
routers/findings.py → regenerate_finding_ai

Role check is done inline in this handler rather than via require_role.

AIClient.analyze_vulnerability() / analyze_reachability() / analyze_severity_override()

Three separate model calls, writing ai_plain_english, reachability(_reason), and ai_severity_override(_reason) onto the Finding row.

get_finding_ai_enrichment

Cache-first: checks Finding.ai_plain_english / scan_metadata["ai_enrichment"] before calling ai/prompt_builder.py:enrich_finding().

Remediation hub

GET …/remediation-hub · POST …/remediation-hub/bulk-pr
get_remediation_hub → per-asset: Trivy findings with ai_remediation set → patch-diff text extracted for UI review create_bulk_pr → validate finding_ids belong to org+asset → consolidate patches → set Finding.pr_url/pr_status
Security note create_bulk_pr generates a fake PR URL (str(uuid.uuid4().int)[:3]) — no actual GitHub call happens here. The real PR creation is a separate endpoint below.

Autofix — open a real PR

POST /findings/{id}/create-fix-pr external I/O
GitHubConfig lookup → utils/encryption.py:decrypt_value(access_token)
git clone (subprocess) → tool-specific fix

Gitleaks: regex-replaces the leaked secret with an env-var lookup, appends to .gitignore. Trivy dependency: bumps package.json/requirements.txt/go.mod. Trivy misconfig: an AI call generates a full replacement file, capped at 50 changed lines.

git commit / push → PyGithub: Github(token).get_repo().create_pull()

Falls back to a simulated PR URL in sandbox mode. Finding.pr_url / pr_status updated either way.

Security note Runs arbitrary subprocess git/npm commands and does regex-based secret scrubbing directly on cloned repo content — gated only by get_current_user, not role-restricted like most other write operations.

Create a Jira ticket

POST /findings/{id}/create-jira-ticket external I/O
JiraConfig lookup → decrypt_value(api_token) → build Atlassian Document Format description → try issuetype Bug → Task → Task(no priority) → httpx POST {base_url}/rest/api/3/issue (Basic auth) → Finding.jira_issue_key → db.commit

07

AI chat agent

Ask a scan a question in plain English; the answer is grounded in real queries, not a free-floating model response.

Ask a question about a scan

POST /scans/{id}/ask ReAct loop · SSE
routers/scans.py → ask_scan_question → ai/agent.py:SecurityAgent(db, scan_id).run_agent(question)

Up to 5 reasoning iterations.

SYSTEM_PROMPT + history → AIClient._call_model_with_model_override()
regex-parse "Action: tool_name(json_args)" → execute_tool()

Dispatches to plain SQLAlchemy queries: list_findings, get_finding, get_scan, get_asset, search_cves — all scoped to self.scan_id.

loop until the model emits "Answer: …"

Citations extracted via a [finding_id: <uuid>] regex, then streamed back to the client in 12-character SSE chunks.

Design note The agent's own tool queries are scoped by scan_id only, not re-checked against org_id — it relies entirely on the org-ownership check already done at the top of ask_scan_question.
08

Dashboard & executive

Dashboard summary

GET /dashboard/summary
routers/dashboard.py → get_dashboard_summary → org-scoped Asset/Scan/Finding queries (windowed by days/timeframe) → posture_score, funnel metrics, MTTR, "do this next" list, trend data
Data quality note This endpoint pads sparse real data with hardcoded fallback values — e.g. total_findings = max(count, 1204) and fabricated demo items with fictional CVE titles. It is not a pure reflection of database state; don't trust its numbers for a real customer org without checking the source.

Executive summary

GET /executive Redis-cached, 5 min
get_executive_summary → Redis cache check (executive:{org_id}) → on miss: _compute_posture_score (-10/critical, -3/high per asset_weight, +1 per fix in last 7d, capped +20) → week-over-week trend + top 5 risks (ranked by KEV, exploit_validated, priority_score) → write back to cache

The cleaner, real-data-only counterpart to the Dashboard endpoint above — no fabricated fallback values here. Its cache is the one save_findings() explicitly invalidates on every new scan.

Admin, intel & integrations

Threat intel status / refresh / AI usage

/admin/intel/* · /admin/ai-usage admin only
get_intel_status → reads Redis keys kev:last_refresh / nvd:* / epss:* for cache freshness force_refresh_intel → intel/kev.py:KEVClient.fetch_and_load_kev() → httpx GET CISA KEV feed (3× backoff) → Redis set kev:cves get_ai_usage → SQL aggregation over AICall joined to Scan/Finding/Org — the surface for every AICall row written across §04/§05/§07

Independent of any HTTP request, celery_app.py's beat schedule also fires tasks/scan_tasks.py:refresh_kev_feed daily at 02:00 UTC.

Integration config — Jira, Slack, GitHub

GET · POST /admin/settings/{jira,slack,github} · …/test admin only
db.query({Jira,Slack,GitHub}Config).filter(org_id==org_id) → on save: utils/encryption.py:encrypt_value() before storing the secret column → GET responses mask the secret as "********"; POST re-decrypts the existing value if the client echoes the mask back unchanged …/test → live connectivity check: Jira.project() / Slack WebhookClient.send() / GitHub get_user() (ghp_mock* tokens simulate a sandbox pass)

GitHub OAuth flow

GET /admin/github/oauth-url · /admin/github/callback
oauth-url → builds the GitHub authorize URL (or a simulated mock-code URL if GITHUB_CLIENT_ID is unset) callback → exchanges code for an access_token → encrypt_value() → GitHubConfig upsert → redirect to /settings#github
Security note The callback is unauthenticated by necessity (it's an OAuth redirect target) and falls back to db.query(Org).first() if no org_id/state param is present — in a real multi-tenant deployment, a dropped state parameter could misattribute a GitHub token to the wrong org.

Cross-cutting risk notes

Things that matter across more than one workflow above, gathered in one place.

AreaDetail
Unauthenticated debug endpointsmain.py and scans.py both expose /test-export-debug and /restart-backend with zero auth — the latter's os._exit(0) is reachable by anyone who can hit the API.
Secrets at restJira / Slack / GitHub credentials are Fernet-encrypted via a single app-wide ENCRYPTION_KEY — but utils/encryption.py has a hardcoded fallback key if that env var is unset. Fine for local dev, dangerous if the fallback ever ships to production.
SSRF guardrouters/scans.py:validate_target() is the only place blocking RFC1918/loopback/localhost targets before they reach an adapter — none of the four adapters re-check this themselves.
AI cost trackingEvery LLM call that passes db= to AIClient._call_model_with_model_override() writes an AICall row, which is what powers /admin/ai-usage. Any call made without db is invisible to that dashboard.
Fingerprint-based upsertsave_findings() is the single convergence point for all four adapters' output — dedup and reconciliation (including auto-marking stale OpenGroup findings fixed) only happens here, never per-adapter.
Demo data in Dashboardrouters/dashboard.py mixes real DB-derived numbers with hardcoded plausible-looking fallback values. /executive does not have this problem — treat it as the source of truth instead.
